# Case format

How a case is written: ruled by the owner 2026-10-30 [the owner's message of 2026-10-30, "d2 yes go on that"], after his reading of the first draft [the owner's message of 2026-10-30: "Most project will have some special feature, like the mpox simulation, so it needs to be flexible and not assume things. maybe distributions should be more flexible"]. It serves roadmap item 2, which showed it to him before any engine code. Its keys, values and the engine's helpers carry the names the owner ruled 2026-10-30.

## The idea

The format fixes only what every cost-benefit analysis shares: the question and options, the time frame and discounting, the inputs with their sources, the cost and benefit streams, and the labelled results. Whatever is particular to a case, such as an outbreak simulation or a traffic model, is that case's own Python and data, in as many modules and tables as it needs. One rule keeps that freedom honest: **every number any of the case's code uses enters as an input with its evidence type**, alone or as a column of an input table, so nothing is hard-coded in a special module (CBA 301 rule 2). Unit constants such as days in a year are the only exception.

## The record of review points

`review/points.toml` is the one record of a case's review points and its limits (roadmap 2.48): every other copy (the comment resolution matrix that opens the author's response letter, the technical appendix's record of points not taken as asked and its limits, the policy paper's list of limits, and the one sentence of review status in the appendix's declaration) is printed from it by the case's documents script, through `review_tables` of `cost_benefit_engine/documents.py`, whose header defines it, and is never typed. It is an array of tables, one per point, each column with one writer:

```toml
[[point]]
id = "fast-E19"                  # the reviewer's number prefixed by the stage that raised it
raised_by = "economics referee"  # from the reviewer's report
point = "bed-days and admissions at average cost"
ruling = "a note in the Limits"  # the editor's, saying who closed the point and on what
state = "closed"                 # the editor's: "open" or "closed"
answer = "accepted: written, with the editor's size"  # the author's: opens with accepted, revised, declined or for the user
where = "appendix 6.3.3"         # the author's: the files and sections the change is in
limit = "Bed-days and admissions are valued at average cost, not at the marginal cost of the days the program saves"
size = "limit_average_cost"      # the author's: the fact in results/facts.json that sizes the limit
size_format = "money"            # the author's: how the size prints, "money" (the default), "percent" or "count"
```

An open row needs `id`, `point`, `raised_by` and `state`; a closed row needs `ruling`, `answer` and `where` besides; `limit` (its text, the editor's, part of the ruling) and `size` come together or not at all, and `size_format` only beside them. A limit no editor has ruled, one the purpose check or the author finds, is a row the author adds with `raised_by` "purpose check" or "author", writing its `limit` and `size`; it prints among the limits at once and stays open until the editor rules on it. A row missing a column its state needs, a column not listed here, an id used twice, or a `size` naming no fact stops the documents script, naming the point or the fact. The tables a template prints, as `{{TABLE <name>}}`: `review_matrix`, every row; `review_record`, the appendix's record of points not taken as asked (`notes/briefs/author_upgrade.md`, message A, 2.1.3), each row that is open, is a limit, or whose answer does not open with "accepted"; `limits_appendix` and `limits_paper`, each limit with its size, the fact's value printed at the case's display figures as `size_format` says: as money by default, as a percentage for "percent" (0.008 prints 0.80% at two figures), or as a plain number for "count"; and `review_status`, the sentence counting the points, closed and open, and the limits. The script then passes each built paper and appendix to `check_document`, which refuses one that does not carry a limit as the record now states it, naming the point, or an appendix without the current status sentence.

## An input

```toml
[colds_per_adult]
label = "Colds per adult per year"
unit = "episodes per adult-year"
distribution = "triangular"
min = 1
mode = 2
max = 4
evidence_type = "single_source"
source = "author_2020"           # a key in sources.toml
quote = "a passage of the source" # verbatim, checked by machine against sources/<key>/text.txt
pinpoint = "Table 2"
sheet = "Colds!B"
```

1. **Distributions:** any of
   1. the template's seven with its parameter names (beta, constant, lognormal, normal, power law, triangular, uniform), so each such input is one column of the sheet;
   2. any distribution in SciPy by its name and parameters (`distribution = "scipy.gamma"`, `a = 2`, `loc = 0`, `scale = 1.5`): gamma, Weibull, Student's t, Poisson, negative binomial and about a hundred more;
   3. **fitted to quantiles**, for elicited judgement: an expert's 5th, 50th and 95th percentiles (or more), turned into a smooth distribution with the metalog family (Keelin 2016, *Decision Analysis* 13(4):243-277), bounded or unbounded as the quantity is;
   4. **empirical:** draws or a table read from a file, such as a simulation model's ensemble or a posterior sample;
   5. **mixture** (competing estimates of one quantity) and **categorical** (a discrete outcome or model structure), each draw picking one by credence weight (CBA 301 rule 9). A mixture's parts are other inputs named by name, each with its own evidence type, source and quote; the mixture only sets their weights (the owner, 2026-10-30).

   Every kind is drawn through its inverse distribution function from the same uniform numbers, so Latin hypercube sampling, a copula for a sourced rank correlation, the sheet's random numbers and the sensitivity analysis treat them all alike. A mixture or a categorical picks its component or outcome by where the uniform number falls among the cumulative weights (a mixture then draws that component at the uniform number rescaled within its share), and the run records which one each draw picked; since that pick does not rise with the uniform number, neither kind takes a rank correlation. A kind the sheet cannot draw goes to the sheet as a pasted column of its draws.

   The keys of each kind (the template's are its own row names; the others were ruled by the owner 2026-10-30):

   | `distribution` | Keys |
   |---|---|
   | `beta`, `constant`, `lognormal`, `normal`, `power law`, `triangular`, `uniform` | the template's: `mean`, `sd`, `min`, `max`, `mode`, `alpha`, `beta`, as each kind uses them |
   | `scipy.<name>` | the distribution's own shape names, and `loc` and `scale`, all required (`loc` only, for a discrete one): nothing falls back to SciPy's defaults |
   | `metalog` | `probabilities` and `values`, two lists of equal length, each value the quantile at its probability; optional `lower_bound`, `upper_bound` and `number_of_terms` |
   | `empirical` | `data_file` and `column`, read into the draws' pool of values |
   | `mixture` | `components`, a table of input name to weight, `{ study_a = 0.6, study_b = 0.4 }`, the weights summing to 1, in the order the uniform number falls through them; each component is an input of its own with its evidence type, source and quote, in the mixture's unit and in no other mixture, and neither a categorical nor indexed by a table; the mixture's own evidence type is the basis of the weights, and a mixture is not indexed by a table |
   | `categorical` | `outcomes`, each outcome with its weight, `{ A = 0.2, B = 0.5, ... }` |

2. **Tables:** an input may be indexed by a table in `data/` (`indexed_by = "sites"`), one draw per row, its parameters and source read from the row's columns. An outbreak model's contact rates by age group are one such table.
3. **Evidence type** (`evidence_type`), with the fields each requires: `single_source`, `several_sources`, `meta_analysis` or `reference_class` (`source` or `sources`, each source with its own `quote`, the quotes in the order of the sources, each quote verbatim, text left out marked by `...` and the parts found in the stored text in that order (the owner, 2026-10-30), and optional `pinpoint`, likewise one per source: a string with `source`, a list with `sources`; `single_source` names its one source by `source`, and `several_sources`, several sources that together bound the value, names two or more by `sources`; where the studies are competing estimates rather than one range, one input per study combined by a mixture: the owner, 2026-10-30); `analyst_judgement`, the analyst's own judgement (`judged_by`, who judged, and `rationale`, the reasoning); `expert_judgement`, a value or range an informant gives in an interview, a survey or correspondence, with `judged_by` (who gave it), `role` and `stake` (the informant's position and what they stand to gain or lose: CBA 301 rule 10), `method` (interview, survey or correspondence), `date` (when asked, a TOML date such as `date = 2026-10-30`; for a survey that ran over several days, the day it closed), `rationale` (the informant's reasoning as given) and `judgement_record` (the file inside the case folder holding the notes, transcript or survey responses; for a survey, each respondent's role and stake are in it) (the owner, 2026-10-30: "yes we will need expert judgment, a lot of things will be based on interviews and surveys", and yes to these fields); an assumption stated in a publication is that publication's `single_source` with its quote; `expert_elicitation` (`experts` and the `elicitation_record`); `ai_expert_panel` (`panel_run_id`, the panel's run, always shown as synthetic); `official_guidance` (`guidance`, a key in `jurisdiction_guidance/`; drawn from the guidance's own low and high where it gives them, as a triangular distribution with the low as its minimum, the value as its mode and the high as its maximum, and held at its value where it does not; the shape ruled by the owner, 2026-10-30: "Do 1.1, it is the simpler thing and the difference is tiny"); `external_model_output` (`file`, the model's output, and `source` or `sources`, the model's citation). A missing field refuses the case when it loads, naming the input and the field; nothing defaults.
4. **Money** declares its currency and its price year by keys of its own on the input, never inside the free-text unit, and an exchange-rate input declares the year of its rate (`rate_year`) and its two currencies, `from_currency` and `to_currency`, an amount in `from_currency` times the rate giving `to_currency` (the owner, 2026-10-30); the engine brings each to the case's price base year by the general price index its jurisdiction's guidance names, then to the case's currency at the exchange rate, an input where the case treats it as uncertain and the guidance's otherwise (not yet built: until an edition holds rates, a rate comes from a case input) (the owner, 2026-10-30; the keys' names follow the naming research of that day). The order is that of the CCEMG and EPPI-Centre cost converter: the price year adjusted in the source currency by its own country's deflator, then the currency converted. The loader resolves each money input's conversion (`cost_benefit_engine/case.py`, `check_money`); multiplying the draws by it is the run's, in `cost_benefit_engine/run.py`. **A probability or share** is bounded to [0, 1], and a draw outside is reported.
   1. `currency`, three upper-case letters such as `AUD`, and `price_year`, a year: both or neither, on any input but an `official_guidance` one, a mixture or a categorical. Each is one value for the whole input; a `{ column = ... }` value is refused, so money that differs row by row in a table is not yet expressible, until a case needs rows in different money.
   2. The two keys declare that the input's value is an amount of that currency at that year's prices: money to the first power, in the numerator. A quantity per unit of money, such as cases averted per million dollars, is entered as its reciprocal, or derived in `model.py` from inputs that are money.
   3. Every price year is a calendar year (the owner, 2026-10-30: "maybe just drop the entire concept of financial year and assume everything is a calendar year"). A price stated for a financial year takes the calendar year holding most of its months, and for a July-to-June year, which splits evenly, the year it ends: "2023-24 dollars" is 2024, and the Green Book's April-to-March "2020-21 prices" is 2020. The difference is at most half a year's inflation, far inside a result's uncertainty.
   4. An `official_guidance` input carries neither key: its money is its guidance entry's `currency` and `price_year` (`jurisdiction_guidance/README.md`). The 2026-10-29 editions and `australia/2024-10-12` state their money in their units, so they cannot supply a money input; a case pins a 2026-10-30 edition for one.
   5. A mixture carries no money keys: each component is converted by its own money, so competing studies in different currencies and years combine. Its components are all money or none, a nested mixture counting as money when its components are.
   6. An exchange-rate input has `from_currency`, `to_currency` (two different currencies) and `rate_year`, all three, and `rate_year` is the case's `price_base_year`, since the rate converts money already in that year's prices. It has no `currency` or `price_year`, and its unit names no currency (`unit = "exchange rate"`): the pair is in `from_currency` and `to_currency`. One rate input serves each pair, and a rate is not inverted: money in USD in a case in AUD needs a rate from USD to AUD. Until the owner rules on them, a rate is neither a categorical, a mixture, a mixture's component nor indexed by a table.
   7. No unit names a currency. A unit is refused, on an input and on a guidance entry an `official_guidance` input uses, when it holds in any letter case, not run into other letters, one of `AUD`, `CAD`, `CHF`, `CNY`, `EUR`, `GBP`, `HKD`, `JPY`, `NZD`, `SGD` and `USD`, the case's currency, or a currency a pinned price index or a rate input names; or a sign, `$`, `£`, `€` or `¥`; or the word `dollar`, `dollars`, `euro`, `euros` or `sterling`. Such a unit marks money whose keys were left off and which would never be converted. Known miss: a currency named only by another code, with no sign or word.
   8. The price step reads the `[price_index]` of the one pinned edition, the case's own or one of `other_guidance_editions`, whose `currency` is the input's: its `calendar_year` value at the case's `price_base_year` over its value at the input's `price_year`. A currency serves one index, the first pinned edition's (the case's own, then the others in order), so money in a currency several countries use (EUR, or US dollars spent outside the United States) is deflated by the one edition that names the currency, not by its own country's deflator, until a later key names a jurisdiction. An input whose currency has no index, or whose years the index lacks, or whose currency has no rate to the case's, is refused.

## The model

```python
def model(inputs, appraisal_years, option):
    """inputs holds each input's draws. Returns each stream named in case.toml as draws by appraisal years, in
    the case's currency and price base year, undiscounted, and each intermediate result as one value per draw."""
```

The engine calls it once per option on the same draws, so each difference from the base case (`base_case`) is computed draw by draw, then discounts and summarises. Inside, the case does whatever its question needs: a chain of stages, a probability of success, a branch on a categorical input's outcome, a schedule computed from a table of tasks, an outbreak simulated draw by draw. The engine also offers helpers a case may import and need not: time shapes (a one-off amount, an annual flow, replacement every n years, a linear phase-in, a stream brought forward: `one_off`, `annual`, `every_n_years`, `linear_phase_in` and `bring_forward` in `cost_benefit_engine.timeline`, each but `bring_forward` taking the number of iterations as the keyword `iterations`, and `appraisal_years` for the years; the names ruled by the owner, 2026-10-30). A helper is added when a second case needs it; until then it lives in the case that wrote it. A case's other modules sit beside `model.py` and are imported relatively (`from . import helpers`). A model that simulates draw by draw will take its random numbers from a fourth argument, `rng`, a `numpy.random.Generator` seeded from the case's `random_seed` and identical for every option, so a run reproduces and options differ only by what they do; it draws in the same order whatever the option, or the options' random numbers fall out of step (the owner, 2026-10-30; not yet built, and until then a model is deterministic in its inputs).

## Scenario runs

Any input can be held at stated values in a scenario run beside the full probabilistic run, for example a key input at its low, central and high values, since readers often want scenarios for the inputs that matter most, while the main run keeps every input a distribution (the owner, 2026-10-30). A scenario names the inputs it holds and the values, each with its source like any input's. The files in `data/` are the tables inputs use, and notes (Markdown or plain text); a data file no input uses is refused.

## What a run gives

For each option against the base case, at each discount rate: present values of costs and benefits, net present value, benefit-cost ratio and the chance it is positive, as means with 5th, 50th and 95th percentiles; partial rank correlations; convergence over the number of iterations, with the share of the mean from the top 1% of draws, since heavy tails (a power law with alpha under 3 has infinite variance) make a mean unstable. Every run checks that net present value equals benefits less costs on every draw, and prints how many inputs rest on each evidence type. Each input and intermediate result carries its sheet column, so the engine can rerun on the sheet's random numbers (`sheet_random_numbers`, item 3's check) and write the case back to a sheet.
