# Sheets: the standard

How a Monte Carlo teaching sheet is built, checked, written into a delivered Google Sheet and reviewed, with the owner's complaints that set each rule. Its tools are `shared/tools/sheets/` in the shared folder (`script`, `importer`, `inplace`, `fill_down.gs` and the stored suite, `suite`), each run as `.venv/bin/python -m tools.sheets.<module>` from the shared folder. Its four parts were four notes of the cost-benefit project until 2026-11-21, when the owner moved the sheet work to the shared folder ("also all the cba work on spreadsheets should be shared, iew will probably need to expoet sheets eventually", 2026-11-21); each keeps its numbering, so a citation such as "register 2.2", "protocol 2.3.6", "route step 4" or "review 4.2" still holds. Its agents are `agents/sheet-layout.md`, which reviews and never writes, and `agents/sheet-twin.md`, which builds. Paths such as cases/<case>/..., notes/..., memories and roadmap ids (R53) name the files of the project that holds the case. (This paragraph is the seat's.)

Every complaint the owner has made about a Google Sheet the project generated or laid out (the project's first teaching sheet, a client's synthesis sheet, his Monte Carlo Template, sheet layout in general), one row per class of fault. Every sheet-script build brief points at this register, runs the whole stored suite (`shared/tools/sheets/suite.py`), and adds a row here and a test there for each new complaint of the owner's.

## Part 2. The twin protocol



In force from 2026-10-31. The owner asked: "Probably we should design an agent definition and protocol for transferring the python to the sheet?", then: "haiku should be able to do the transfer work, and it's a lot cheaper", and that the agent "is unique to this project and should only live here". He named it `sheet-twin`; its definition is `agents/sheet-twin.md`.

### 1 Why

1.1 A case has a sheet where the user asks for one (`.claude/skills/scope-case/presets.md` 10.3, step 1). Its purpose is its readers. The owner, the owner's message of 2026-11-10 (point d): "the sheet twin mainly exists to make it easier for people to audit the code, and for the model to be shared. the redundant build is not the main point and probably is not an effective error catching technique." Until then this section gave the reason as "one inspector finds half its errors or fewer" (`notes/owner_cba_rules.md`, the owner's rule 2; Panko 2000, 5.3 below), with every case built twice and each version checking the other. The twin check of 2.1.4 stays, because it shows that the sheet people audit is the model that was run.

1.2 Building a sheet twin is about half judgement: how the model's expectations become columns, the sums over years, the twin check. The other half is mechanical: header rows, the Variables and Sources rows, formatting, a loop of recorded runs.

1.3 So the protocol splits the work: the judgement into a written spec by the case's author; the building and the standing checks to Haiku, working from the spec. The checks of 2.4, fixed before the build, are what let a cheaper model's sheet be trusted.

### 2 The protocol

2.1 **The spec**, written by the case's author (until 2026-11-12 by the coordinator; one author writes all of a case's analysis, CORE 5.3), one file per case, `cases/<case>/sheet_spec.md`:

2.1.1 Every tab, and in each every column: its name, symbol, unit, formula in words, and the Python function it twins. Where a column needs MAP and LAMBDA, the spec gives the formula itself, which the author writes.

2.1.2 How each part of the Python becomes a sheet column, and every simplification with its effect, sized or marked far inside the result's uncertainty (CORE 1.5).

2.1.3 The settings and the recorded runs to make (the seat's list).

2.1.4 The twin check: the settings held to match a named Python run, the quantity compared, and the tolerance, fixed before the sheet exists: two combined standard errors, unless a difference listed under 2.1.2 moves the quantity, which the spec then sizes.

2.1.5 The bridge: the steps, one setting at a time, from the Python's headline to the sheet's.

2.1.6 Any choice in the spec that sets a method or can move a result goes to the referee first, as every such decision does (`CLAUDE.md`).

2.2 **The inputs and sources rows** are generated by a script from the case's `inputs.toml` and `sources.toml` (each input's distribution, parameters, link and quote; each source's citation and link), so no number is retyped. Each input and each factor is drawn in the form its own file names (`kind` in `inputs.toml`, `form` in `estimates.toml`, chosen by `notes/factor_forms.md`), the form the Python draws, and its header row names that form, so a reader sees what shape each range has and the twin check compares like with like. The script is built through `build` at standard risk.

2.3 **The build**, by the agent, in the layout `shared/tools/sheets/script.py` writes (the seat's reading of his sheet conventions). The layout meets the modelling codes' common rules:

2.3.1 Inputs apart from calculations, and calculations apart from results: the Globals and Tables tabs hold inputs, the model tabs the calculations, Results the answer, Audit the checks (FAST 1.01-01; ICAEW Code, principle 9).

2.3.2 One formula per column: the 1,000 draw rows (2.3.5) hold the draws, each row its column's one formula over the cells of its own row, with no array formula (the owner, 2026-11-16: "The array formulas are an impediment to understanding"), so every formula is consistent along its column (FAST 3.02-01, "Formulas must be consistent"; ICAEW principle 12).

2.3.3 No number typed into a formula: fixed data sit in the Tables tab with each block's source (FAST 3.04-01; ICAEW principle 14; his rule 2 in `notes/owner_cba_rules.md`, from his post "CBA 301: Practical Advice").

2.3.4 A user guide and the checks inside the workbook: the Readme, the Variables tab, the Audit tab (ICAEW principles 7 and 17; FAST 2.04-03, "self-documenting Input sheets").

2.3.5 The sheet conventions (the seat's design; no words of his in the register state them): a header above the draws (name; note; formula in words or quote; distribution and parameters; the low end, mean and high end of the draws; a histogram), rows 1 to 15 in the layout `shared/tools/sheets/script.py` writes, one row one purpose, and on a tab with a method of one column two more, Credence and Cumulative share, inserted above the notes, a tab without one having none (register 5.2); draws by the hash formula, MOD(SIN(ROW*12.9898 + COLUMN*78.233 + SHEET*37.719)*43758.5453, 1) from the row below the header on, row 16 or, on a tab with the two rows, row 18, as `shared/tools/sheets/script.py` (`sheet_uniforms`) states it; inputs in blue.

2.3.6 Readable without scrolling. The owner: "the current draft has columns that are too wide, meaning more scrolling is needed, and the rows with text should be longer" (2026-10-31). Type: Arial 10 in every cell of every tab, a tab's title alone set apart by bold at a larger size (the owner, 2026-11-20, choosing it on the spreadsheet-style sources, research/refs.toml keys cfi_financial_modeling_guidelines, ssrb_2026_bpms_overview, fast_2019_standard: "a, my old order was confused", replacing his 2026-10-31 "at least 11"). Font colour marks a cell's kind (the owner, Decision 23, 2026-11-20, choosing option A: "a"): input blue for a value someone may change, black for a formula, green for another tab's cell carried over unchanged (a plain reference such as =Globals!C13, or a lookup that returns such a cell), and black for every formula that computes, whatever tab its arguments sit on (the seat's rule, for the percentile rows that read the Guide's interval setting), and every hyperlink on every tab the normal hyperlink blue, underlined (the owner, 2026-11-20, overruling the seat's earlier choice for links: "no everyone expects hyperlinks to be blue. Use normal hyperlink blue for them and a different blue for inputs, and make sure the explanation sheet has the convention, with examples"); the Guide carries a colour key with one row per kind: a sample in its colour, a plain sentence, and a real example cell of that kind from the sheet; his Monte Carlo Template's red and green text, which no file explained, is replaced by it. The seat's choices, not his: link blue #1155CC (Google's own link colour), underlined; input blue #0000FF, never underlined; green #008000; Results and Sensitivity otherwise black. Input and model tabs keep his template's column widths and alignment, which the sheet script's look constants copy: shown a sheet restyled to these rules, he wrote "the new teaching sheet is horribly bad, you killed all the formatting and messed up all the cell sizes" and "the template is still fine, things should look like this", and then "left justify the mins (7 and 13 on templater) right justify the maxes and center the means" (2026-11-16). A model-tab column is widened only where its widest displayed value needs it. Rows 1 to 3 wrap, aligned to the top. The header fits one screen: the rows above the first draw row are together short enough that it, and the formula in it, shows on a laptop without scrolling. The owner, 2026-11-16: "please shrink the citation and notes boxes so I can see all the way to the formula on a laptop, and make this a standard rule. Try to keep the size of my example". And, shown the result at his template's exact heights: "you can give them more space than that, unbold and increase size so we can see as much of the text as possible, subject to the constraint that you can still see 3 lines of calculations". So the rows above the first draw row total at most about 420 px, which on his laptop (about 490 px of grid) leaves three draw rows in view; the height beyond the template's goes to the text rows (the tab's note, the names, the citations and notes), and the header's text is not bold, so that more of it shows. A citation or note longer than its box wraps inside that fixed height and is cut off at its foot, read whole by selecting the cell, and no header row is grown to fit its text. Row 12 (histograms) is about 80 px, and the iteration rows fit one line. Text tabs (Readme, Variables, Sources, Results, Audit): text wraps in the tab's wide column, which is no wider than 600 px; a title or paragraph that sits in a narrow column gets that column widened, never a merge, and is never left wrapped inside a narrow column (a title wrapped inside a narrow column breaks its words; The owner, 2026-11-20, replacing the merge rule: "the actual rule is to widen the column if you can, merging causes all kinds of mess"); the rows fit their content. Numbers carry their unit's format: "apply formatting where appropriate especially percentages and money figures" (the owner, the same session): a probability or share as a percentage, money with its currency sign and thousands separators, a year with no separator, and every number a reader sees at two significant figures, by its own rounding formula where no formula reads its cell and by its number format where one does. Every number is the unit it claims: no format scales a value; a money column's numbers are stored in its declared unit (thousand, million, billion or trillion of its currency), named in words in its column's name and note; a formula that reads another unit carries the factor; and a number that is not money and is 10,000 or more shows in scientific notation, on model tabs as on every other (part 4 of this standard, 4.2, which holds the rule and the owner's words on it). The layout review, part 4 of this standard, checks all of this after the build.

2.4 **The standing checks**, by the agent, each recorded with its date in the Results tab. Their names follow the verification checklist TECH-VER (Büyükkaramikli et al. 2019).

2.4.1 An error sweep: an ISERROR count over every tab, zero.

2.4.2 A white-box test, the Audit tab: one iteration recomputed year by year in plain cell formulas beside the model's own sums, at three iterations the spec names so that each branch runs; every difference zero to rounding.

2.4.3 Black-box tests at extreme values, where the answer is known without the model: for example, with the policy's effect set to zero, the benefits must be zero in every iteration and the net present value minus the policy's cost.

2.4.4 The twin check of 2.1.4. It is verification (Eddy et al. 2012: "check accuracy of coding"), not validation: the two versions share the spec, so they can be wrong together (Knight and Leveson 1986). The model's validity rests on the design's cross-checks against sources and on the referee.

2.4.5 The bridge of 2.1.5, whose factors multiply to the gap between the two headlines.

2.4.6 The recorded runs of 2.1.3: a setting changed, the headline read, the setting restored, and the headline back to its last digit.

2.5 **The report**, by the agent: the link; the headline and how it was computed; each check's reading; every departure from the spec; and `STATUS: BLOCKED` for anything it could not represent truly, never an approximation the spec does not list.

2.6 **The coordinator's reading**: the Results tab and the check readings, not the whole sheet, and one Audit iteration of its own choosing.

### 3 Weighing the checks (`standards/process/controls.md`)

3.1 The Audit tab and the twin check are the kind of check that file names worth having: an independent reimplementation, judged against the other (its section "What makes a check worth having", item 2; Herndon et al. 2014 found the error in Reinhart and Rogoff's spreadsheet by replication). TECH-VER ranks replication the costliest verification step, "recommended only in certain situations"; here the sheet is built for its readers, so the check adds only the cost of comparing the two.

3.2 Each can fail: a wrong window in a sum over years shows as a nonzero difference in 2.4.2; a benefit leaking past a zero response shows in 2.4.3; the tolerance of 2.1.4 is fixed before the run.

3.3 Each costs one to four connector calls on a build that already runs, and none runs again until the model changes. The error sweep and the restore guard against a sheet delivered with an error cell or left at a non-headline setting, a fault the owner would see first.

3.4 Nothing here gates commits or other work. Review date: after the third sheet twin; a check stays only where it changed something.

### 4 The agent

4.1 `sheet-twin`, on Haiku, defined in `agents/sheet-twin.md`: it builds from the spec and runs the checks of 2.4; it writes only to the sheet the spec names.

4.2 Whether a subagent reaches the Google connectors is untested. The first use tests it, and an agent that cannot reach them reports `STATUS: BLOCKED`.

## Part 3. The in-place route



A seat writing a regenerated version into a delivered sheet follows this route, when the evidence calls for keeping the file: others hold its link or have worked in it. The memory `update-a-delivered-sheet-in-place.md` says when a file is edited and when it is replaced, and that a few cells are edited by hand. The owner, 2026-11-20: "From now on it should be editing the exiting sheet instead of making a new file each time. People will be working on it and linking to it."; 2026-11-21: "Base it on evidence of people looking at it. If nobody has opened it, then it can be repalces, But if people left comments in you need to preserve that or ask about replacing." The helper `shared/tools/sheets/inplace.py` writes the files; the connector calls stay the seat's. Commands below run from the shared folder with `.venv/bin/python -m tools.sheets.inplace`.

Inputs: the live sheet's id and recorded title, the case's `model/out/live_snapshot.json` (the last write's snapshot), the deployed xlsx (the one whose sha256 the snapshot records, from git at the commit the case's `deliverables/upload.md` names) and the new generated `sheet.xlsx`.

1. Metadata check. Drive `get_file_metadata` on the live id: not trashed, and its title is the recorded one. A trashed or renamed target stops the route and is reported.
2. Pre-read. `get_spreadsheet` with `includeGridData`, one call per tab and row range (more than about 3 MB in one read closes the connector), each saved to a file: column tabs rows 1 to 16, the Guide whole, Results rows 1 to 60, Sensitivity in two reads (1 to 60, 61 to 120), and any tab the team added. Fields: `sheets.properties,sheets.data.startRow,sheets.data.startColumn,sheets.data.rowData.values.userEnteredValue,sheets.data.rowData.values.effectiveValue` (dotted paths; parenthesised lists are refused). A read that does not cover the snapshot's `rows_read` shows its unread cells as deleted.
3. `diff SNAPSHOT GRID...`. It sees only the rows it is given (the header rows, Results to 60, Sensitivity to 120), while step 7's paste covers the whole tab, so exit 0 does not mean the draw rows are unedited. Exit 0: no edits, go on. Exit 1: the table on stdout lists each cell (tab, cell, was, now), each tab added, deleted or renamed, and each change in a tab's row or column count (a row inserted or deleted below the rows read shows only there; a snapshot taken before 2026-11-21 records no counts, so that write's diff cannot see it); stop and report it, so the case author carries what should stay into the data file and regenerates, or the owner rules. A tab of the team's own is kept by the route (nothing below touches it), but it is still reported.
4. `plan OLD.xlsx NEW.xlsx --live META.json --snapshot SNAPSHOT --old-columns OLD.tsv --new-columns NEW.tsv --out DIR`, where OLD.tsv and NEW.tsv are the generator's `columns.tsv` written with each xlsx (the deployed one from git at the same commit), META is a `get_spreadsheet` of the tab list (no grid data); it refuses an OLD whose sha256 is not the one the snapshot records. A tab the new version renames is stated with `--rename OLD=NEW`, once per tab; the helper never guesses one, so without it the old tab is listed as dropped and the new one as added. `DIR/plan.json` names the changed tabs, and those renamed, added and dropped: read the dropped and added lists, and where a pair is really a rename, run again with `--rename`. If `DIR/before_copies.json` exists, apply it now with `update_spreadsheet`, before any copy: it renames live tabs and adds each new tab empty under its name, so copied formulas that cite those names resolve rather than come over as `#REF!`.
5. Upload the new xlsx with Drive `create_file` as a scratch Google Sheet (the owner's My Drive, not the team's drive), and copy each tab `plan.json` lists as changed into the live file with `copy_sheet_to_another_spreadsheet`. That call sometimes answers "Internal error" after succeeding: list the tabs before retrying.
6. Read the tab list again (META) and write `COPIES.json`, `{tab name: sheetId of its "Copy of" tab}`. Run `plan` again with the same arguments and `--live META.json --copies COPIES.json`. It refuses a copy missing from the list.
7. Apply `DIR/batch_1.json`, `batch_2.json`, ... in number order, each as one `update_spreadsheet` body. Before each tab's paste they restructure it natively by column id: the columns the new version drops are deleted, those it adds inserted, those that move moved. The team's comments on header cells stay with their cells under a native delete, insert or move, not under a paste, which leaves a comment or a link on its cell while another column's content lands under it; a column the new version drops is deleted with its comments, and `plan` names each such column on stderr. Then they paste each copy onto its live tab (PASTE_NORMAL, then PASTE_DATA_VALIDATION, from A1 over the larger of the old and new extents, so old surplus cells are cleared), set column widths, row heights and frozen panes from the new xlsx (copyPaste does not carry them), put the tabs in the new order where it changed and delete the copies. A tab the new version adds is pasted onto the empty tab step 4 made. A tab it drops is named in `plan.json` and left for the seat to delete after checking that no formula of the team's cites it. Then trash the scratch file.

9. `snapshot GRID... --out model/out/live_snapshot.json --xlsx NEW.xlsx` on the post-read.
10. The `sheet-layout` look (`agents/sheet-layout.md`), the last step of every write. The look reports; it writes nothing to the sheet. A fault it finds goes to the generator (the script, its layout files or the data file), and the next regeneration carries the fix. Nothing is fixed live (the owner, 2026-11-21: "the process when finding a flaw in anything generated shuold always be to fix the generator, never hand edit one of its outputs").
11. Commit the snapshot with the case and record the write in the case's `deliverables/upload.md`.

### 1 Why

1.1 Without it, layout faults reach the owner, who finds them by eye: for example, columns too wide, or words broken across lines in a narrow column, which a rule that every text cell wraps can cause. Each costs him a look, a screenshot and a message.

1.2 Neither fault shows in the values the sheet-twin agent reads back, so its checks (protocol 2.4) cannot see them.

### 2 What exists

Searched 2026-10-31. Nothing lints or fixes the layout of a Google Sheet:

2.1 Spreadsheet Preflight, a Workspace add-on, checks sheets against rules it does not publish.

2.2 ExceLint (Barowy, Berger and Zorn, OOPSLA 2018) and Formula Foundry find formula errors, not layout.

2.3 The xlsx-verify skill renders an Excel file and lints it; it does not read Google Sheets.

2.4 The Sheets API resizes rows and columns to their content (`autoResizeDimensions`): a fix, not a check.

The standards exist and the checker does not, so the review applies the standards by rule, then by eye.

### 3 The standard

3.1 Schwabish, J. (2020), "Ten Guidelines for Better Tables", *Journal of Benefit-Cost Analysis* 11(2): 151–178, doi:10.1017/bca.2020.11, the field's own journal. The guidelines applied here: offset the heads from the body (1); right-align numbers and their heads (3); left-align text and its heads (4); show the precision the reader needs (5); guide the eye with space (6); put the unit in the head, not in every cell (7).

3.2 The modelling codes the protocol already cites (FAST; ICAEW) for one format per column and inputs styled apart from calculations.

3.3 The owner's rulings: Arial 10 in every cell, a tab's title alone bold and larger (his "a", the owner's message of 2026-11-20, choosing the seat's Decision 19 option A, which set both), while model and input tabs keep his template's widths and alignment (protocol 2.3.6; his words on alignment, the owner's message of 2026-11-16: "left justify the mins (7 and 13 on templater) right justify the maxes and center the means"; that the template's widths stay is the seat's reading, beside his the owner's message of 2026-11-20: "keep the columns narrower like before if possible"); narrow columns and text rows tall enough to read in place (his the owner's message of 2026-10-31: "The current draft has colums that are too wide, meaning more scrolling is needed, and the rows with text should be longer"); percentages and money formatted (the owner's message of 2026-10-31: "apply formatting where appropriate especially percentages and money figures"); the header rows of his own sheets (protocol 2.3.5).

### 4 The checks

Each is a rule over the grid's metadata (`spreadsheets.get` with grid data: effective format, width, height, wrapping, merges), then a look at the render.

4.1 Type: every cell Arial 10, a tab's title alone bold and larger. Model and input tabs keep the template's widths and alignment (mins left, means centred, maxes right); do not restyle them. Font colour marks a cell's kind (his "a", the owner's message of 2026-11-20, choosing the seat's Decision 23 option A, "blue for a value someone may change, black for a formula and green for a formula that reads another tab" [the seat's text; its green superseded by register 1.4]): input blue for a value someone may change, black for a formula, green for another tab's cell carried over unchanged (a plain reference or a lookup returning one; a formula that computes is black whatever tab it reads; protocol 2.3.6), and every hyperlink on every tab the normal hyperlink blue, underlined (the owner, 2026-11-21, overruling the seat's earlier choice for links: "no everyone expects hyperlinks to be blue. Use normal hyperlink blue for them and a different blue for inputs, and make sure the explanation sheet has the convention, with examples"); the Guide carries a colour key with one row per kind: a sample in its colour, a plain sentence, and a real example cell of that kind from the sheet; his template's red and green text, which no file explained, is replaced by it. The seat's choices, not his: link blue #1155CC (Google's own link colour), underlined; input blue #0000FF, never underlined; green #008000; Results and Sensitivity otherwise black. The check reads each cell's effective font colour against its kind.

4.2 Formats by unit: a probability or share as a percentage; money with its currency sign and thousands separators; a year with no separator; a count with separators. Every number is the unit it claims. No number format scales a value: no trailing comma, which divides the shown number by 1,000, and no scale letter or word. So every cell shows the number it holds, and a typed input shows the number typed (the owner, 2026-11-21, the cost-benefit project's an earlier session, R63, of a cell typed 2,677,000 that showed 2,677 under "(₩ trillion)", its note in another unit: "somehow through horrible black magic the displayed number is much less than the typed number?!"; then: "just make everything consistently the unit it claims to be, and use a reasonable unit! then you can convert to a new unit later that's properly declared"). A column's heading and its note name the same unit, and a column's unit is read from its head and from the Variables tab.

4.2.1 Money. A money column (its data unit names a currency) has one declared unit, a currency and a scale (₩ trillion, $ million), named in words in its heading ("Real GDP (₩ trillion)") and as the first money unit of its note, never by a letter in the cells ("2.7M", which a reader takes as 2.7 million won; R57 round 5). Its stored values, an input's parameters and the draws, are in that unit. The data file may set the unit (`unit`); otherwise it is the smallest of units, thousands, millions, billions and trillions, that puts the column's typical value (the mean of its draws' absolute values) between 1 and 9,999 (the seat's default, not his words). Trillion is the largest unit (the owner, the same session: "go back to trillion being the highest unit, the reason for going to quadrillion was dumb. just use trillion and keep a 2 sigfig max"). The case's data gives each value in its source's unit, the column's data unit, and the generator converts it into the column's unit once, at generation ("(₩ Bil)" over 2,677,000 becomes "(₩ trillion)" over 2,677). A column may state its data unit as a field of the data file; where stated, the field governs; a note's prose never sets a unit (register 4.16); absent the field, the data unit comes from the column's name (its first unit in brackets, else its group label's, else dollars for the `$` kind; `data_unit`). The reason: while a note could set it, a rewrite of a case's notes silently turned 207 money columns into non-money (R63). The field and its precedence are the seat's, from his "properly declared" (4.2). This holds on every tab, model tabs included (the owner, 2026-11-20 local, transcript line 173, not yet in the register: "fix the generator so it lists numbers in million or billion or trillion when appropriate, this is bad and the earlier sheets we made did better").

4.2.2 Conversions. A formula that reads a column in another unit carries the conversion as an explicit factor at that reference (`C16*1000`), and the reading column's note names it ("Conversions: C is ₩ trillion, × 1,000 to ₩ billion."), so a number changes unit only where the change is declared. A run of money on a table or on Sensitivity takes the unit that shows its largest number under 1,000 (the seat's), by a factor in its cells' formulas where no other cell of the table cites them, named in its head; a mean and its interval share one unit.

4.2.3 Large numbers that are not money. A number that is not money and whose size is 10,000 or more (the threshold is the seat's) shows in scientific notation at two figures, `0.0E+0`, so 17,126 shows 1.7E+4: a column's draws and rows 12 to 14 at its typical size, and each typed number of that size (the owner, the same session: "first, anything not money that is a large number should default to scientific notation. that solves most problems"). A literal format the data file gives is applied as written, and it too scales nothing.

4.2.4 Two figures. Every number a reader sees (an input's parameters, rows 12 to 14, the draws, Results, Sensitivity and every table) shows two significant figures (2,970,000,000 dollars shows 3.0 under "($ billion)", never 2.97; the owner, 2026-11-20 local, transcript line 229, of "2.97 billion": "no that's 3 sigfigs which I know I've complained about before too and this forgot"). A cell no formula reads (a terminal cell: Results, a table, an option tab's summary rows nothing cites) is computed to two figures by its own formula, `ROUND(x, 1 - INT(LOG10(ABS(x))))` with zero guarded (`IF(x = 0, 0, ...)`), so 4,237 trillion shows 4,200; a cell any formula reads keeps full precision and gets its two figures from its number format (the owner, 2026-11-21, the cost-benefit project's an earlier session, R63: "You can totally write code to round things in results, it's pretty simple, you just use dynamic round and log. I did this all the time in earlier sheets. And it's fine to round any terminal displayed value that nothing else uses as an input"; that every terminal cell is so rounded, joining these words with his two-figure rule, is the seat's reading). In a cell a formula reads, a whole number shows all its whole figures, since a format chooses decimals only (4.14; the seat's reading of his words, the owner's message of 2026-11-16: "sometimes this won't work because it only lets you choose decimals"; register 2.2 and 2.3). Kept exact: a year, a label, the draw numbers in column A.

4.3 No word broken across lines: in a wrapped cell, the longest word is narrower than its column (estimated as characters × 0.55 × the size in pixels, plus 10 px of padding; the factor is checked against the render).

4.4 No paragraph in a narrow column: text that would wrap past about five lines in a column under 150 px gets its column widened (a text column up to 600 px), or moves to the tab's wide column; never a merge (the five lines, the 150 px and the 600 px are the seat's). The owner, the owner's message of 2026-11-20, replacing the merge rule: "the actual rule is to widen the column if you can, merging causes all kinds of mess".

4.5 Nothing hidden: no text clipped by a filled neighbour, no number shown as `###`. The one exception is a citation or note cut off at the foot of its fixed-height header row (4.7).

4.6 Alignment: numbers right, text left, each head aligned with its column.

4.7 Widths and heights as the protocol's 2.3.6 sets them. The header rows keep their fixed heights, at most about 420 px together, so that three draw rows show under them on a laptop screen (about 490 px of grid) without scrolling, and are never grown to fit their text; every other row is tall enough for its wrapped text.

4.8 Heads: row 1 frozen, and in the model tabs column A too; a sheet built on his template keeps the template's panes. Header text is not bold, so that more of it shows (4.7; part 2 of this standard 2.3.6).

4.9 Table tabs: no error value (#N/A, #VALUE!, #REF!) in any cell, every number formatted (4.2), every interval text at two significant figures.

4.10 A column's note is true of what the column now holds: a note copied from an imported sheet that names another currency, unit or source than the column's is a fault of content, reported (register 4.2).

4.11 A sheet's headline compares its result with the bar of the best other use of the money, as the owner's original sheet compared its benefit-cost ratio with GiveWell's top charities (the owner, 2026-10-31: "the headline result should compare the benefit cost ratio to givewell top charities, like the original sheet did at the end"); the generalisation to the best other use of the money, and the reporting of a sheet without one, are the seat's (register 6.7).

4.12 In a client sheet converted to the template, a fact a statistics office publishes (a salary, a population, a price) is sourced, not judged (the owner, 2026-11-20: "why would you just make something up for basic facts like korean researcher salary instead of finding a source?"); a judged input whose fact is published is reported (register 6.6).

4.13 In a section of a number format that has a condition (`[<=-0.005]0.00`), Google Sheets shows a negative value's minus itself, so a "-" written in that section shows it twice ("--0.2" for -200,000 on a live client sheet, 2026-11-21). A format with a condition writes no "-" of its own (register 2.2; the generator's `signed_zero`, and the suite's "2.2 one minus").

4.14 A number format chooses decimals, never significant figures, and scales nothing (4.2). So in a cell a formula reads, which keeps full precision, a whole number shows all its whole figures: from 100 to 9,999 in its column's unit on a column tab, and past 9,999 only in trillions, which have no unit above them (12,345 trillion shows 12,345 under "(₩ trillion)"); a cell no formula reads takes its two figures from its rounding formula instead (4.2.4; register 2.2 and 2.3; the generator's `draws_format`, `set_format` and `column_size`). (4.13 and 4.14 are the seat's, from what the builds of 2026-11-21 found.)

### 5 The render

5.1 The Drive connector exports the whole workbook as one PDF, laid out as Google draws it (`download_file_content` with `exportMimeType` `application/pdf`); `pdftoppm` turns its pages into images, and `pdftotext` finds the first page of each tab by the tab's title text. The export shows a fault of layout as a screenshot of the sheet does.

5.2 The reviewer looks at the first page of each tab against section 4, and at what no rule sees: a head that reads badly, a block that should be grouped, a chart cut off.

5.3 Render, look, render once more and look again: two renders at most. The reviewer writes nothing to the sheet; it reports what the renders show, as findings (6).

### 6 What it reports, and to whom

6.1 The reviewer reads the sheet and reports each fault as a finding. It never writes to the sheet: no `update_spreadsheet`, and no other route into it.

6.2 Each finding names the cells (tab and range), the fault as Google displays it, the part of the generator that made it (the script `shared/tools/sheets/script.py`, its template or layout files, or the case's data file) and what the fix there would be.

6.3 The faults are of formats, fonts, widths, heights, wrapping, alignment, merges and frozen panes, which the generator sets. A fault of content (a wrong value, a display formula that prints the wrong thing) is a finding for the case's author, as before.

6.4 The seat that dispatched the review sends the findings to a `build` of the generator, or to the case's author for a data-file fault. It then regenerates and writes the sheet by the normal route (part 3 of this standard for a delivered sheet). A sheet already live that carries the fault stays as it is until that regeneration.

### 7 Who runs it, and when

7.1 After the sheet-twin's build and checks (protocol 2.4), before the owner sees the sheet.

7.2 A different seat from the builder, on Sonnet: the builder makes the faults, and the review must look at images and judge them.

7.4 Every upload or in-place write of a sheet ends with this look before anyone is told the sheet is ready (register 8.1); a fault it finds is reported (6) and goes to a build of the generator, which fixes it in the script or the data file and adds its test to the suite (register 8.2); the next regeneration carries the fix, and nothing is fixed live. A new sheet's upload carries the fill-down script too: install `shared/tools/sheets/fill_down.gs` in the sheet and set `fill_down_script = true` in the Guide (his "note that r8 worked in [a client's sheet] but then it did not get added to others", 2026-11-21, the R8 item; the step's place here is the seat's, since no step of the route uploads a new sheet).

7.6 The note delivered beside a changed sheet lists what changed, briefly, and no results comparison (the owner, 2026-11-20: "the change document should just be about what actually changed, not a results comparison"; register 8.6).

7.3 The rules of section 4 become a script over the saved grid metadata once a trial run has shown which of them catch real faults; the script then runs inside the sheet-twin's build as well, so that most faults never reach the reviewer.

### 8 Weighing (CORE rule 10; the shared `standards/process/controls.md`)

8.1 What it catches, for the generator to fix: faults like those of 1.1, and the size and formats the owner asked for on 2026-10-31 (the owner's message of 2026-10-31: "make the font size at least 11, I look at this on a laptop" and "apply formatting where appropriate especially percentages and money figures"; the size is since superseded, 3.3).

8.2 What it costs: one Sonnet run reading the grid metadata and about fifteen page images a round, two rounds at most; the script, once written, costs nothing to run. Against that, each fault that reaches the owner costs him a look, a screenshot, a message and a rebuild round.

8.3 A trial run measures the cost and records which check found what; a check that finds nothing in three builds is weighed again.
