# The protocol for building a case's sheet twin

In force from 2026-10-31. The owner asked: "Probably we should design an agent definition and protocol for transferring the python to the sheet?", then: "haiku should be able to do the transfer work, and it's a lot cheaper", and that the agent "is unique to this project and should only live here". He named it `sheet-twin`; its definition is `.claude/agents/sheet-twin.md`.

## 1 Why

1.1 A case has a sheet where the user asks for one (`.claude/skills/scope-case/presets.md` 10.3, step 1). Its purpose is its readers. The owner, the owner's message of 2026-11-10 (point d): "the sheet twin mainly exists to make it easier for people to audit the code, and for the model to be shared. the redundant build is not the main point and probably is not an effective error catching technique." Until then this section gave the reason as "one inspector finds half its errors or fewer" (`notes/owner_cba_rules.md`, the owner's rule 2; Panko 2000, 5.3 below), with every case built twice and each version checking the other. The twin check of 2.1.4 stays, because it shows that the sheet people audit is the model that was run.

1.2 Building a sheet twin is about half judgement: how the model's expectations become columns, the sums over years, the twin check. The other half is mechanical: header rows, the Variables and Sources rows, formatting, a loop of recorded runs.

1.3 So the protocol splits the work: the judgement into a written spec by the case's author; the building and the standing checks to Haiku, working from the spec. The checks of 2.4, fixed before the build, are what let a cheaper model's sheet be trusted.

## 2 The protocol

2.1 **The spec**, written by the case's author (until 2026-11-12 by the coordinator; one author writes all of a case's analysis, CORE 5.4), one file per case, `cases/<case>/sheet_spec.md`:

2.1.1 Every tab, and in each every column: its name, symbol, unit, formula in words, and the Python function it twins. Where a column needs MAP and LAMBDA, the spec gives the formula itself, which the author writes.

2.1.2 How each part of the Python becomes a sheet column, and every simplification with its effect, sized or marked far inside the result's uncertainty (CORE 1.5).

2.1.3 The settings and the recorded runs to make (the seat's list).

2.1.4 The twin check: the settings held to match a named Python run, the quantity compared, and the tolerance, fixed before the sheet exists: two combined standard errors, unless a difference listed under 2.1.2 moves the quantity, which the spec then sizes.

2.1.5 The bridge: the steps, one setting at a time, from the Python's headline to the sheet's.

2.1.6 Any choice in the spec that sets a method or can move a result goes to the referee first, as every such decision does (`CLAUDE.md`).

2.2 **The inputs and sources rows** are generated by a script from the case's `inputs.toml` and `sources.toml` (each input's distribution, parameters, link and quote; each source's citation and link), so no number is retyped. Each input and each factor is drawn in the form its own file names (`kind` in `inputs.toml`, `form` in `estimates.toml`, chosen by `notes/factor_forms.md`), the form the Python draws, and its header row names that form, so a reader sees what shape each range has and the twin check compares like with like. The script is built through `build` at standard risk.

2.3 **The build**, by the agent, in the layout `tools/sheet_script.py` writes (the seat's reading of his sheet conventions). The layout meets the modelling codes' common rules:

2.3.1 Inputs apart from calculations, and calculations apart from results: the Globals and Tables tabs hold inputs, the model tabs the calculations, Results the answer, Audit the checks (FAST 1.01-01; ICAEW Code, principle 9).

2.3.2 One formula per column: rows 16 to 1,015 hold the draws, each row its column's one formula over the cells of its own row, with no array formula (the owner, 2026-11-16: "The array formulas are an impediment to understanding"), so every formula is consistent along its column (FAST 3.02-01, "Formulas must be consistent"; ICAEW principle 12).

2.3.3 No number typed into a formula: fixed data sit in the Tables tab with each block's source (FAST 3.04-01; ICAEW principle 14; his rule 2 in `notes/owner_cba_rules.md`, from his post "CBA 301: Practical Advice").

2.3.4 A user guide and the checks inside the workbook: the Readme, the Variables tab, the Audit tab (ICAEW principles 7 and 17; FAST 2.04-03, "self-documenting Input sheets").

2.3.5 The sheet conventions (the seat's design; no words of his in the register state them): a header above the draws (name; note; formula in words or quote; distribution and parameters; the low end, mean and high end of the draws; a histogram), rows 1 to 15 in the layout `tools/sheet_script.py` writes, one row one purpose; draws by the hash formula, MOD(SIN(ROW*12.9898 + COLUMN*78.233 + SHEET*37.719)*43758.5453, 1) from row 16 on, as `cost_benefit_engine/sampling.py` (`sheet_uniforms`) states it; inputs in blue.

2.3.6 Readable without scrolling. The owner: "the current draft has columns that are too wide, meaning more scrolling is needed, and the rows with text should be longer" (2026-10-31). Type: Arial 10 in every cell of every tab, a tab's title alone set apart by bold at a larger size (the owner, 2026-11-20, choosing it on the spreadsheet-style sources, research/refs.toml keys cfi_financial_modeling_guidelines, ssrb_2026_bpms_overview, fast_2019_standard: "a, my old order was confused", replacing his 2026-10-31 "at least 11"). Font colour marks a cell's kind (the owner, Decision 23, 2026-11-20, choosing option A: "a"): input blue for a value someone may change, black for a formula, green for another tab's cell carried over unchanged (a plain reference such as =Globals!C13, or a lookup that returns such a cell), and black for every formula that computes, whatever tab its arguments sit on (the seat's rule, for the percentile rows that read the Guide's interval setting), and every hyperlink on every tab the normal hyperlink blue, underlined (the owner, 2026-11-20, overruling the seat's earlier choice for links: "no everyone expects hyperlinks to be blue. Use normal hyperlink blue for them and a different blue for inputs, and make sure the explanation sheet has the convention, with examples"); the Guide carries a colour key with one row per kind: a sample in its colour, a plain sentence, and a real example cell of that kind from the sheet; his Monte Carlo Template's red and green text, which no file explained, is replaced by it. The seat's choices, not his: link blue #1155CC (Google's own link colour), underlined; input blue #0000FF, never underlined; green #008000; Results and Sensitivity otherwise black. Input and model tabs keep his template's column widths and alignment, which the sheet script's look constants copy: shown a sheet restyled to these rules, he wrote "the new sheet is horribly bad, you killed all the formatting and messed up all the cell sizes" and "the template is still fine, things should look like this", and then "left justify the mins (7 and 13 on templater) right justify the maxes and center the means" (2026-11-16). A model-tab column is widened only where its widest displayed value needs it. Rows 1 to 3 wrap, aligned to the top. The header fits one screen: the rows above the first draw row are together short enough that it, and the formula in it, shows on a laptop without scrolling. The owner, 2026-11-16: "please shrink the citation and notes boxes so I can see all the way to the formula on a laptop, and make this a standard rule. Try to keep the size of my example". And, shown the result at his template's exact heights: "you can give them more space than that, unbold and increase size so we can see as much of the text as possible, subject to the constraint that you can still see 3 lines of calculations". So the rows above the first draw row total at most about 420 px, which on his laptop (about 490 px of grid) leaves three draw rows in view; the height beyond the template's goes to the text rows (the tab's note, the names, the citations and notes), and the header's text is not bold, so that more of it shows. A citation or note longer than its box wraps inside that fixed height and is cut off at its foot, read whole by selecting the cell, and no header row is grown to fit its text. Row 12 (histograms) is about 80 px, and the iteration rows fit one line. Text tabs (Readme, Variables, Sources, Results, Audit): text wraps in the tab's wide column, which is no wider than 600 px; a title or paragraph that sits in a narrow column gets that column widened, never a merge, and is never left wrapped inside a narrow column (a title wrapped inside a narrow column breaks its words; The owner, 2026-11-20, replacing the merge rule: "the actual rule is to widen the column if you can, merging causes all kinds of mess"); the rows fit their content. Numbers carry their unit's format: "apply formatting where appropriate especially percentages and money figures" (the owner, the same session): a probability or share as a percentage, money with a dollar sign and thousands separators and its unit in the head, a year with no separator, and every number a reader sees at two significant figures, by its number format, never by rounding a value, a large one in a scaled unit (thousand, million, billion, trillion) chosen from its column's or block's values and named in words in its column's name or its table's head, never by a letter in the cells (R57 round 5), model tabs included (the owner, 2026-11-20: "fix the generator so it lists numbers in million or billion or trillion when appropriate", and of "2.97 billion": "no that's 3 sigfigs"; `notes/sheet_layout_review.md` 4.2). The layout review, `notes/sheet_layout_review.md`, checks all of this after the build.

2.4 **The standing checks**, by the agent, each recorded with its date in the Results tab. Their names follow the verification checklist TECH-VER (Büyükkaramikli et al. 2019).

2.4.1 An error sweep: an ISERROR count over every tab, zero.

2.4.2 A white-box test, the Audit tab: one iteration recomputed year by year in plain cell formulas beside the model's own sums, at three iterations the spec names so that each branch runs; every difference zero to rounding.

2.4.3 Black-box tests at extreme values, where the answer is known without the model: for example, with the policy's effect set to zero, the benefits must be zero in every iteration and the net present value minus the policy's cost.

2.4.4 The twin check of 2.1.4. It is verification (Eddy et al. 2012: "check accuracy of coding"), not validation: the two versions share the spec, so they can be wrong together (Knight and Leveson 1986). The model's validity rests on the design's cross-checks against sources and on the referee.

2.4.5 The bridge of 2.1.5, whose factors multiply to the gap between the two headlines.

2.4.6 The recorded runs of 2.1.3: a setting changed, the headline read, the setting restored, and the headline back to its last digit.

2.5 **The report**, by the agent: the link; the headline and how it was computed; each check's reading; every departure from the spec; and `STATUS: BLOCKED` for anything it could not represent truly, never an approximation the spec does not list.

2.6 **The coordinator's reading**: the Results tab and the check readings, not the whole sheet, and one Audit iteration of its own choosing.

## 3 Weighing the checks (`standards/process/controls.md`)

3.1 The Audit tab and the twin check are the kind of check that file names worth having: an independent reimplementation, judged against the other (its section "What makes a check worth having", item 2; Herndon et al. 2014 found the error in Reinhart and Rogoff's spreadsheet by replication). TECH-VER ranks replication the costliest verification step, "recommended only in certain situations"; here the sheet is built for its readers, so the check adds only the cost of comparing the two.

3.2 Each can fail: a wrong window in a sum over years shows as a nonzero difference in 2.4.2; a benefit leaking past a zero response shows in 2.4.3; the tolerance of 2.1.4 is fixed before the run.

3.3 Each costs one to four connector calls on a build that already runs, and none runs again until the model changes. The error sweep and the restore guard against a sheet delivered with an error cell or left at a non-headline setting, a fault the owner would see first.

3.4 Nothing here gates commits or other work. Review date: after the third sheet twin; a check stays only where it changed something.

## 4 The agent

4.1 `sheet-twin`, on Haiku, defined in `.claude/agents/sheet-twin.md`: it builds from the spec and runs the checks of 2.4; it writes only to the sheet the spec names.

4.2 Whether a subagent reaches the Google connectors is untested. The first use tests it, and an agent that cannot reach them reports `STATUS: BLOCKED`.
