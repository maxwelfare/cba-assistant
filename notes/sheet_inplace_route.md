# Writing a new version into a delivered Google Sheet: the route

A seat writing a regenerated version into a delivered sheet follows this route, when the evidence calls for keeping the file: others hold its link or have worked in it. The memory `update-a-delivered-sheet-in-place.md` says when a file is edited and when it is replaced, and that a few cells are edited by hand. The owner, 2026-11-20: "From now on it should be editing the exiting sheet instead of making a new file each time. People will be working on it and linking to it."; 2026-11-21: "Base it on evidence of people looking at it. If nobody has opened it, then it can be repalces, But if people left comments in you need to preserve that or ask about replacing." The helper `tools/sheet_inplace.py` writes the files; the connector calls stay the seat's. Commands below run from the project root with `.venv/bin/python -m tools.sheet_inplace`.

Inputs: the live sheet's id and recorded title, the case's `model/out/live_snapshot.json` (the last write's snapshot), the deployed xlsx (the one whose sha256 the snapshot records, from git at the commit the case's `deliverables/upload.md` names) and the new generated `sheet.xlsx`.

1. Metadata check. Drive `get_file_metadata` on the live id: not trashed, and its title is the recorded one. A trashed or renamed target stops the route and is reported.
2. Pre-read. `get_spreadsheet` with `includeGridData`, one call per tab and row range (more than about 3 MB in one read closes the connector), each saved to a file: column tabs rows 1 to 16, the Guide whole, Results rows 1 to 60, Sensitivity in two reads (1 to 60, 61 to 120), and any tab the team added. Fields: `sheets.properties,sheets.data.startRow,sheets.data.startColumn,sheets.data.rowData.values.userEnteredValue,sheets.data.rowData.values.effectiveValue` (dotted paths; parenthesised lists are refused). A read that does not cover the snapshot's `rows_read` shows its unread cells as deleted.
3. `diff SNAPSHOT GRID...`. It sees only the rows it is given (the header rows, Results to 60, Sensitivity to 120), while step 7's paste covers the whole tab, so exit 0 does not mean the draw rows are unedited. Exit 0: no edits, go on. Exit 1: the table on stdout lists each cell (tab, cell, was, now), each tab added, deleted or renamed, and each change in a tab's row or column count (a row inserted or deleted below the rows read shows only there; a snapshot taken before 2026-11-21 records no counts, so that write's diff cannot see it); stop and report it, so the case author carries what should stay into the data file and regenerates, or the owner rules. A tab of the team's own is kept by the route (nothing below touches it), but it is still reported.
4. `plan OLD.xlsx NEW.xlsx --live META.json --snapshot SNAPSHOT --old-columns OLD.tsv --new-columns NEW.tsv --out DIR`, where OLD.tsv and NEW.tsv are the generator's `columns.tsv` written with each xlsx (the deployed one from git at the same commit), META is a `get_spreadsheet` of the tab list (no grid data); it refuses an OLD whose sha256 is not the one the snapshot records. A tab the new version renames is stated with `--rename OLD=NEW`, once per tab; the helper never guesses one, so without it the old tab is listed as dropped and the new one as added. `DIR/plan.json` names the changed tabs, and those renamed, added and dropped: read the dropped and added lists, and where a pair is really a rename, run again with `--rename`. If `DIR/before_copies.json` exists, apply it now with `update_spreadsheet`, before any copy: it renames live tabs and adds each new tab empty under its name, so copied formulas that cite those names resolve rather than come over as `#REF!`.
5. Upload the new xlsx with Drive `create_file` as a scratch Google Sheet (the owner's My Drive, not the team's drive), and copy each tab `plan.json` lists as changed into the live file with `copy_sheet_to_another_spreadsheet`. That call sometimes answers "Internal error" after succeeding: list the tabs before retrying.
6. Read the tab list again (META) and write `COPIES.json`, `{tab name: sheetId of its "Copy of" tab}`. Run `plan` again with the same arguments and `--live META.json --copies COPIES.json`. It refuses a copy missing from the list.
7. Apply `DIR/batch_1.json`, `batch_2.json`, ... in number order, each as one `update_spreadsheet` body. Before each tab's paste they restructure it natively by column id: the columns the new version drops are deleted, those it adds inserted, those that move moved. The team's comments on header cells stay with their cells under a native delete, insert or move, not under a paste, which leaves a comment or a link on its cell while another column's content lands under it; a column the new version drops is deleted with its comments, and `plan` names each such column on stderr. Then they paste each copy onto its live tab (PASTE_NORMAL, then PASTE_DATA_VALIDATION, from A1 over the larger of the old and new extents, so old surplus cells are cleared), set column widths, row heights and frozen panes from the new xlsx (copyPaste does not carry them), put the tabs in the new order where it changed and delete the copies. A tab the new version adds is pasted onto the empty tab step 4 made. A tab it drops is named in `plan.json` and left for the seat to delete after checking that no formula of the team's cites it. Then trash the scratch file.
8. Post-read, as in step 2, and compare the final distributions: rows 12 to 14 of every column tab and every number of Results against the twin (`tools.sheet_script` load and compute on the data file). Check the link and title are unchanged and that no error value shows.
9. `snapshot GRID... --out model/out/live_snapshot.json --xlsx NEW.xlsx` on the post-read.
10. The `sheet-layout` look (`.claude/agents/sheet-layout.md`), the last step of every write. The look reports; it writes nothing to the sheet. A fault it finds goes to the generator (the script, its layout files or the data file), and the next regeneration carries the fix. Nothing is fixed live (the owner, 2026-11-21: "the process when finding a flaw in anything generated shuold always be to fix the generator, never hand edit one of its outputs").
11. Commit the snapshot with the case and record the write in the case's `deliverables/upload.md`.
