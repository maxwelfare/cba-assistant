Order of work: read the grid metadata with field masks (formats, widths, heights, merges), never the whole grid at once; check it by rule; then render and look; judge what the render shows; render once more; stop after two renders.

Working rules for reading and judging:

1. Read a cell's type size, formats, widths, heights and merges by dotted-path field masks (`userEnteredFormat.textFormat.fontSize` and the like), so each read is small; the connector rejects parenthesised masks and closes on a read above about 3 MB.
2. Judge a whole column or block at once, never cell by cell, and report it as one finding with its range: the report is the cost.
3. A number pattern with a sign needs its negative section written out (`$#,##0;-$#,##0`); a single pattern with a minus sign in it prints the sign twice. Report a pattern that does either.
0. Type size, merging and the model tabs' widths and alignment follow `notes/sheet_twin_protocol.md` 2.3.6 and `notes/sheet_layout_review.md` 4.1 and 4.4; a finding never asks to restyle model and input tabs. Font colour marks a cell's kind (input blue a value someone may change, black a formula that computes (whatever tab it reads), green another tab's cell carried over unchanged (a plain reference or a lookup returning one), and every hyperlink on every tab the normal hyperlink blue, underlined; the Guide carries a colour key with one row per kind): the rule, the Guide's key and the seat's marked choices (link blue #1155CC, input blue #0000FF, green #008000) are `notes/sheet_twin_protocol.md` 2.3.6.
4. Where a column cannot widen, report it (see 0).
5. A tiny negative that rounds to zero shows as a zero with a minus sign: the finding is that the column needs more precision or a zero section.
6. A long note may make a row taller than the protocol's target; shortening it changes content, so it is a finding for the case's author.
6.1. When Google refuses the sheet's PDF export (too large), judge by grid metadata and displayed values, read per tab in row ranges with dotted-path field masks; render rules then do not apply.
7. Find each tab's first page in the exported PDF with `pdftotext`, render only those pages (`pdftoppm -r 80`), and look at each one.

Each finding names three things: the cells (tab and range); the fault as Google displays it; and the part of the generator that made it, with the fix there. The part is one of: `tools/sheet_script.py` (the function or table that sets the format), its template or layout files, or the case's data file (`sheet.toml` or the file the script reads). Find it by reading the script; where you cannot find it, say so and give your best reading, marked as one. A fault of content (a wrong value, a display formula that prints the wrong thing, a stale reference written in a cell) is a finding for the case's author, with which part you think made it, the sheet or its spec.
